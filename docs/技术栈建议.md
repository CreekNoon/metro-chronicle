# 技术栈建议（写给这个项目的后续演进）

> 现状：单文件 HTML（Leaflet 1.9.4 + GSAP + 自绘 canvas 线路层），双击 `file://` 即可运行，
> 底图三级兜底（高德栅格 → OpenFreeMap 矢量 → Esri 栅格），编辑/持久化/可选后端都已具备。
> 本文回答一个问题：**如果要更顺滑、更省心、更好交付，应该换成什么技术栈。**

---

## 一、这个项目真正的技术需求

| 需求 | 权重 | 说明 |
|---|---|---|
| 中文底图（可离线/可缓存） | 高 | 高德栅格最省事，但有 GCJ-02 偏移与限流；离线交付最好自带瓦片 |
| 60fps 镜头与线路延伸动画 | 高 | 这是当前所有 bug 的来源：DOM/SVG 逐帧重绘 |
| 单文件双击可用 | 中高 | 目前是硬约束（用户场景：发个 HTML 就能看） |
| 站点/线路编辑与持久化 | 中 | 已实现（localStorage + 可选 Node 后端） |
| 可导出视频/分享 | 低 | 未来可能想要"纪事片" |

结论：**渲染层是唯一必须换的东西**，数据模型、交互模型、HUD 设计都可以原样保留。

---

## 二、候选方案对比

| 方案 | 帧率 | 中文底图 | 离线 | 单文件 | 迁移成本 | 适用场景 |
|---|---|---|---|---|---|---|
| **A. 现状：Leaflet + canvas** | 40–60（软件合成时 30–50） | 高德栅格 ✓ | 需缓存 | ✓ | 0 | 维持现状，已优化到底 |
| **B. MapLibre GL JS + 栅格/矢量瓦片** | 60（GPU） | 高德栅格 / 天地图 / OpenFreeMap | 需缓存 | 需打包 | 中（2–3 天） | 想彻底解决帧率、又要联网 |
| **C. MapLibre + 自带 PMTiles 瓦片包** | 60（GPU） | 可自制（OSM/天地图切片） | **✓ 完全离线** | ✓（单文件 10–30MB） | 中高（3–5 天） | **推荐给"交付产品"** |
| **D. Tauri + MapLibre + 本地瓦片** | 60（GPU） | 同上 | ✓ | 安装包 | 高（1–2 周） | 要做桌面客户端 |
| **E. Remotion（React + FFmpeg）** | 逐帧确定性渲染 | 叠在地图录像上 | ✓ | 输出 MP4 | 高 | 要做宣传片/纪事片 |
| **F. Flutter + maplibre_gl** | 60 | 同上 | ✓ | 安装包 | 很高（重写 UI） | 要上移动端 App |

### A. 现状（Leaflet + canvas）：什么时候别换
- 必须"一个 HTML 文件、双击就开、不能联网安装任何东西"；
- 地图只需要 2–3 个城市、几条线路；
- 能接受"软件渲染时 30–50fps"。

已经做了这些优化后，它就是这套技术栈的天花板：
`_rawPanBy` 纯 transform 平移、canvas 只描已揭示段、按层级缓存投影点、
瓦片分批预取 + IndexedDB 缓存、跨层缩放一次动画到位。

### B/C. MapLibre GL JS：最值得换的一步
为什么它能一次性解决你现在遇到的所有问题：

| 你的痛点 | MapLibre 里的现成答案 |
|---|---|
| 线路延伸"一段段"、帧率低 | 线路是一个 **GPU 绘制的 LineLayer**；揭示进度用 `line-gradient`（`lineMetrics: true` + 动态 stops）或 `line-dasharray` 偏移，**每帧只改一个绘制属性**，不重建几何 |
| 缩放/平移不平滑 | `map.easeTo({center, zoom, duration, essential:true})` 由 GPU 合成；`map.flyTo` 自带抛物线飞行与 padding 控制 |
| 站名标签互相压住（自写避让算法） | `symbol` 层自带 **collision detection** + `text-allow-overlap:false` + `symbol-sort-key` 优先级，不用自己算 |
| 换乘站多色圆环 | `circle` 层 + `expression` 按 lineKeys 数量取色；或用 `icon` 层 + `SDF` |
| 底图缓存/离线 | `pmtiles://` 协议直接读单文件瓦片包（z0–14 的湖南省约 100–200MB，只切株洲/湘潭约 10–30MB） |
| 编辑与预览 | `GeoJSONSource.setData()` 热更新，编辑时不需要重建图层 |

**推荐组合（联网版）**：`TypeScript + Vite + MapLibre GL JS + Zod（数据校验）+ Zustand（状态）`
**推荐组合（离线交付版）**：上面 + `pmtiles`（自建瓦片包，`tippecanoe`/`planetiler` 切片）+ 单文件打包（Vite `vite-plugin-singlefile`）

### D. Tauri（要桌面客户端时）
- Rust 壳 + WebView2，安装包 ~5MB，比 Electron 轻一个数量级；
- 可直接读本地 PMTiles/MBTiles 文件，甚至内置一个小的瓦片 HTTP 服务；
- 前端代码与 B/C 完全一致，只多一层壳。

### E. Remotion（要输出视频时）
- 用 React 描述每一帧，FFmpeg 渲染，**逐帧确定性**、可批量导出 4K；
- 适合"把这条纪事片导成 MP4 发出去"的场景；可复用同一份城市/线路 JSON。

### F. Flutter（要上手机 App 时）
- `maplibre_gl` 或 `flutter_map`，性能好，但要重写全部 UI 与编辑交互；
- 只有在"必须原生 App"时才值得。

## 三、如果继续留在 Web，我建议的**渐进式迁移路径**

1. **第 1 步（1 天，零风险）**：把现在这份代码抽成 `data/*.json`（城市、线路、站点、日期）与
   `render/`（渲染层），数据模型不变 —— 为换渲染器做准备。
2. **第 2 步（2–3 天）**：新增 `render/maplibre.js` 实现同一套接口（`build/fit/flyTo/drawProgress/revealStation`），
   用 URL 参数 `?engine=maplibre` 切换，两套渲染器并存、逐项比对（现有 21 套断言可直接复用来验收）。
3. **第 3 步（1–2 天）**：把瓦片换成 PMTiles 单文件包，去掉联网依赖与 GCJ-02 偏移问题。
4. **第 4 步**：如果还要桌面交付，用 Tauri 包一层；如果要视频，用 Remotion 复用同一份数据。

这样任何一步都可以回滚，且每一阶段都有测试兜底。

---

## 四、一句话结论

- **想省事、就按现状交付**：已经把这套栈优化到极限（自绘 JS < 1ms/帧，底图之外 59–60fps）。
- **想要真正的高帧率与更好的地图体验**：换成 **MapLibre GL JS**（GPU 渲染 + 内置标签避让 + 渐变线揭示），
  离线交付再加 **PMTiles** 单文件瓦片包。
- **要桌面端** → Tauri 包一层；**要视频** → Remotion 复用同一份数据。
